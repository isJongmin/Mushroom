## 2. 끊김 원인과 수정

| 실서버 로그 | 원인 (코드) | 수정 |
|---|---|---|
| `ClientPresenceRateLimitReached` | 이동할 때마다 정지 600ms 뒤 `track()`(어댑터 `scheduleTrack` + room.js `updateSelf({x,y})` 두 경로). 좌우를 오가면 초당 여러 번 Presence 전송 | track은 입장 1회 + 닉네임/아바타 변경 때만, 어댑터 전체에서 최소 2초 간격(대기 요청은 하나로 합침). 위치는 move로만. 새 멤버의 presence join → 기존 멤버가 현재 상태를 move로 1회(`onPeerJoin` → 다음 송신 기회에 announce, 여러 명이면 1회로 합침). 나가기 때 untrack도 보내지 않음(removeChannel의 leave로 충분) |
| `Unauthorized … room:<id>` (join_room 응답 약 3초 전 구독) | (1) realtime-js는 오류 난 채널을 1·2·5·10초 뒤 **스스로 다시 구독**한다. 우리 재연결 코드도 같은 채널을 removeChannel 없이 두거나 join_room 없이 다시 구독했다. (2) room.js `connect()`의 12초 `Promise.race` 시간 초과 후 늦게 성공한 채널은 아무도 닫지 않아 고아 채널이 계속 자동 재구독. (3) 나가기는 `leave_room`을 1.5초만 기다리고 로비로 가서, 바로 다시 들어가면 늦게 처리된 leave가 새 멤버 행을 지울 수 있었다. (4) 이전 채널 removeChannel이 끝나기 전에 같은 topic 새 채널 생성 가능 | (1) 구독 후 CHANNEL_ERROR/TIMED_OUT/CLOSED → 어댑터가 즉시 removeChannel(자동 재구독 타이머 정지) 후 `onDrop` → 상태기계가 join_room → 새 구독. (2) 모든 시도에 세대 번호 + AbortSignal, 늦게 온 채널은 즉시 close. (3) 나가기 = 채널 정리 → leave_room 순서, 어댑터는 진행 중 leave가 끝날 때까지(최대 8초) 다음 join/create를 미룸. (4) 진행 중 removeChannel이 끝날 때까지(최대 5초) 새 채널을 만들지 않음 |

## 3. 상태기계 (`backend/room-link.js`)

```
idle → connecting → connected ⇄ rejoining | reconnecting → lost | failed | closed
```
- 시도 = (이전 채널 close 완료) → `join_room` 'OK' → 구독(SUBSCRIBED + 첫 track). 첫 시도만 join 생략(로비/새로고침이 이미 OK를 받음). 시도는 한 줄로만 실행 → 동시에 열린 채널 최대 1개.
- 세대 번호 gen: 끊김·재입장·닫기마다 증가. 늦게 끝난 join/open은 버리고, 그때 열린 채널은 즉시 close(`stats.stale`).
- 끊김(onDrop) / 시도 실패 → 백오프 1, 2, 4, 8, 16, 30, 30…초(성공하면 처음부터). 화면: 배너 "연결이 끊어졌어요. 다시 연결하는 중..."(대기 4초 이상이면 "지금 연결" 버튼 → `reconnectNow`), 성공하면 배너 숨김 + 로그 "다시 연결됐어요" + 빠진 메시지 병합.
- join_room이 ROOM_NOT_FOUND/ROOM_FULL/NICK_TAKEN/NICK_FORMAT/WRONG_PASSWORD/RATE_LIMITED → `lost`("로비로").
- 하트비트 20초(상태기계 타이머). NOT_MEMBER → `rejoining`(배너 없이 join → 구독, 기존 규칙: 끊김마다 1회, 직전 시도 10초 안이면 남은 시간 뒤). 일시 오류로 실패하면 reconnecting 백오프로 넘어간다(이전: 곧바로 lost).
- 첫 연결 3번 실패 → `failed`(화면 fatal "다시 시도" → `retry()`, join부터).
- `check()` (visibilitychange → visible): 연결 중이면 즉시 하트비트 + `conn.healthy()`(supabase: `ch.state === 'joined' && realtime.isConnected()`)가 거짓이면 끊김 처리, 백오프 대기 중이면 바로 시도.
- `close()`: 대기·하트비트 중지, 진행 중 시도 abort, removeChannel과 진행 중 시도가 끝날 때까지 기다림(화면 정리는 최대 2초만 기다리고, 그 뒤 순서는 어댑터가 보장).

### 어댑터 인터페이스 변경 (ARCHITECTURE 결정 6 갱신 요청)
- `connectRoom(roomId, handlers, self, { signal }) → { sendMove, updateSelf, healthy, close, leave(= close) }`
- handlers: `onSync, onJoin, onLeave, onPeerJoin(user_id), onMove, onChat, onDrop(status)`. `onStatus`는 없어짐.
- 하트비트·재시도·재입장은 어댑터가 아니라 `room-link.js`가 한다.
- 계측 `backend.stats = { track, moveSent, subscribe, removeChannel, joinRoom, leaveRoom, drops }`.

### move payload
`{ user_id, x, y, dir: 'left'|'right', s: 'idle'|'walk'|'jump'|'fall'|'crouch' }`, x/y는 정수 반올림. 위치·방향·상태 중 하나라도 바뀌었을 때만, 최대 10회/초(화면 100ms + 어댑터 throttle, 마지막 값은 반드시). 점프 중에는 y가 계속 바뀌어 10회/초로 나간다. local(BroadcastChannel)도 같은 payload.
수신(`physics.cleanMove`): x 유한수 필수, y는 [240, 440]로 자름(없으면 440), s가 목록 밖이면 null(→ idle/walk는 실제 움직임으로 추정).
원격 보간: x는 기존 추적. 세로는 받은 (y, s)에서 `|vy| = sqrt(650² − 2·2000·(440 − y))`로 속도를 되살려 같은 물리로 시뮬레이션하고, 차이가 8 이상일 때만 다시 맞춘다(오차는 80ms 감쇠로 이어 붙임). Presence sync보다 먼저 온 move는 보관했다가 그 사람이 목록에 생길 때 적용.

6. 재연결(local 훅): 같은 방 BroadcastChannel `mushroom:room:<roomId>`로 `{type:'debug-drop', user_id, fail:2}` → 배너, 약 7초 뒤 복구, `net.link.events`에서 매 시도 join → join-ok → open.
7. 늦게 들어온 사람이 기존 멤버의 현재 위치를 바로 봄(Presence 입장값 아님).
8. 실서버(외부망): 계속 이동해도 `ClientPresenceRateLimitReached`/Unauthorized 로그 없음, 나가기 → 즉시 재입장, 방 옮기기, 모바일 백그라운드 복귀 후 자동 복구, Supabase 대시보드에서 클라이언트당 Presence 메시지 수.
9. 누수: 입퇴장 반복 후 BroadcastChannel/interval/rAF 증가 없음(e2e 20), 재연결 반복 후 열린 채널 1개.

## 8. 알려진 한계
- supabase 모드는 코드 리뷰 + 상태기계 단위 시험으로만 확인. realtime-js 2.45의 자동 재구독·`ch.state` 값은 소스 기준 추정.
- 나가기를 1.5초 기다린 뒤 로비로 가는 동안 상태기계가 진행 중 join을 기다리고 있으면, 그 뒤에 보내는 leave_room은 로비의 다음 입장보다 늦게 시작될 수 있다(드묾).
- pagehide의 `untrack` 1건은 계측(`track`)에 넣지 않았다.
- 원격 세로 위치는 패킷 지연만큼(보통 100~150ms) 늦게 보인다.
